# Aurea Hosting — Internal Site Audit
**Date:** 22 April 2026  
**Scope:** All files in project root, reviewed in full

---

## Executive Summary

The site is well-structured, with consistent navigation, thorough SEO metadata on all public pages, clean JavaScript, and a thoughtful CMS system. The most significant issues are a silent CMS wiring bug (admin edits to FAQ items 5–8 are lost), a WCAG AA colour contrast failure on gold text, and a duplicate map initialisation that produces console errors on the Areas page. There are also several orphaned admin panel fields that do nothing when edited, which will cause confusion when content updates are needed. No Lorem ipsum, no broken links, no missing pages in the user-facing funnel.

**SHOULD-FIX — Straight apostrophes in cms.js founder letter**  
_Affects: cms.js lines 238–240 (founderLetterP2, founderLetterP3)_

The founder letter paragraphs in `cms.js` use straight apostrophes (`'`) while the rest of the site (and the CMS defaults for other content) correctly uses Unicode curly quotes (`'`). Because the founder letter paragraphs are injected by the CMS into `data-content` elements, the rendered page will show straight apostrophes in the letter body.

Affected strings include `"it's"`, `"it's"`, `"We're"`, and `"we've"` in founderLetterP2 and founderLetterP3. Replace with `’` (right single quotation mark).

### 3. Technical Audit

**CRITICAL — FAQ items 5–8 CMS keys defined but not wired to HTML**  
_Affects: faq.html lines 200–245, cms.js lines 226–233_

The CMS defines `faq5Q`, `faq5A` through `faq8Q`, `faq8A`. The admin panel (admin.html tabs FAQ5–FAQ8) has input fields for all of these. However, the HTML elements for FAQ items 5–8 in `faq.html` do **not** have `data-content` attributes:

```html
<!-- FAQ 5 — no data-content on the span or p -->
<button class="faq-question" aria-expanded="false">
  <span>How does dynamic pricing work?</span>  ← missing data-content="faq5Q"
```

Items 1–4 are correctly wired (`data-content="faq1Q"`, `data-content="faq1A"`, etc.). Items 5–8 are hardcoded. Any changes made in the admin panel to FAQ 5–8 are silently discarded — they are never applied to the page.

**Fix:** Add `data-content="faq5Q"` to the `<span>` in each FAQ 5–8 button, and `data-content="faq5A"` to the `<p>` inside each answer div. Repeat for 6, 7, 8.

---

**SHOULD-FIX — Multiple admin panel hero fields not wired to inner-page HTML**  
_Affects: admin.html (sections Why Us, Areas, Apply, FAQ, Services, Technology), and the corresponding HTML files_

The admin panel has input fields for `whyHeroTitle`, `whyHeroText`, `areasHeroTitle`, `areasHeroText`, `contactHeroTitle`, `contactHeroText`, `faqHeroTitle`, `faqHeroText` (and implicitly the services/technology hero copy). None of these `data-content` attributes exist on the `<h1>` or `<p class="hero-type-sub">` elements of their respective pages.

For example, why-us.html line 67:
```html
<h1 class="hero-type-headline">The comparison<br>is straightforward.</h1>
```
Has no `data-content="whyHeroTitle"`. Same pattern on areas.html, contact.html, faq.html.

**Impact:** The admin panel gives the false impression these fields are editable. They are not.

**Fix (two options):** Either add the `data-content` attributes to the HTML elements (preferred), or remove the orphaned admin fields to avoid confusion.

**SHOULD-FIX — Areas page initialises MapLibre map twice, causing console errors**  
_Affects: areas.html lines 346–377 (inline IIFE) and app.js lines 281–309_

`areas.html` includes an inline `<script>` at the bottom of `<body>` containing an IIFE that creates a `maplibregl.Map` on `#aurea-map`. Then `app.js` also runs on `DOMContentLoaded` and makes a second `maplibregl.Map` call on the same container element. MapLibre throws an error when a second map is initialised on an occupied container. The visible map still works (it uses the first init), but the console shows errors on every Areas page load.

**Fix:** Remove the MapLibre init code from either the inline IIFE in `areas.html` or from `app.js`. Keep one, delete the other. The `app.js` version is slightly more complete (more markers, includes West Beach) so keep that one and remove the IIFE.

**SHOULD-FIX — Hero background image in index.html hosted on Unsplash CDN**  
_Affects: index.html line 134_

```html
src="https://images.unsplash.com/photo-1600596542815-ffad4c1539a9?w=1200&q=85&auto=format&fit=crop"
```

This is a hotlinked Unsplash image. Unsplash currently permits hotlinking, but there is no contractual guarantee — if the photo is removed or Unsplash changes its hotlinking policy, the homepage hero goes blank with no warning. Download the image, save it to `images/hero-home.jpg`, and serve it locally.

**SHOULD-FIX — Aurea-Owner-Agreement.html and Aurea-Owner-Appointment-Form.html don't load app.js**  
_Affects: Aurea-Owner-Agreement.html, Aurea-Owner-Appointment-Form.html_

Neither legal document page loads `app.js`. Both include the site navigation with a mobile hamburger button (`.nav-toggle`), but the toggle event listener is registered in `app.js`. On mobile, the hamburger does nothing on these pages. Add `<script src="app.js"></script>` and `<script src="cms.js"></script>` before `</body>` on both pages.

---

**SHOULD-FIX — Owner legal pages lack noindex meta tag**  
_Affects: Aurea-Owner-Agreement.html, Aurea-Owner-Appointment-Form.html_

Both pages are disallowed in `robots.txt`, which is good. However, `robots.txt` is a courtesy that compliant crawlers follow — it is not enforced. Neither page has `<meta name="robots" content="noindex, nofollow">`. If a link to these documents ever appears on an external site, a crawler that ignores `robots.txt` could index them. Add the meta tag to both:

```html
<meta name="robots" content="noindex, nofollow">
```

(`admin.html` already has this correctly.)

**SHOULD-FIX — MailerLite embed CSS contains an empty property value**  
_Affects: report.html line 466_

```css
.g-recaptcha {
  height: ;   ← empty value, invalid CSS
}
```

This is invalid CSS (value-less property). Browsers tolerate it, but it will flag in any CSS validation run and could behave unexpectedly in strict parsing contexts. Remove the `height` declaration entirely, or set a real value.

---

**NICE-TO-HAVE — Intel strip HTML is hardcoded in index.html AND regenerated by cms.js**  
_Affects: index.html lines 226–250, cms.js renderIntelStrip()_

The ticker content is hardcoded as two sets of HTML cards in `index.html`. On page load, cms.js then rebuilds the entire ticker innerHTML from the `intelEvents` array, overwriting the hardcoded HTML. This means the hardcoded HTML is never actually seen by users — it exists only as a flash before JavaScript runs — but it creates a maintenance trap: if someone updates the hardcoded HTML thinking they're changing the ticker, cms.js silently overwrites their change.

The hardcoded HTML in `index.html` can be removed; the ticker works entirely from cms.js data.

### 5. Accessibility

**CRITICAL — Gold text on light backgrounds fails WCAG AA colour contrast**  
_Affects: All pages — section kickers, insight eyebrows, report-eyebrow, admin-header-badge_

Gold (`#c8a35d`) on the sand background (`#fffdf9`) produces a contrast ratio of approximately **2.2:1**. WCAG 2.1 Success Criterion 1.4.3 requires **4.5:1** for normal text and **3:1** for large text (18pt+ or 14pt+ bold). The section kickers (e.g. "The Process", "Coverage", "Audience") are rendered at approximately 11–12px with letter-spacing — well below the large-text threshold. They fail at the current colour.

This affects every page on the site. The brand guide would need to decide between:
- Darkening the gold to approximately `#9a7a3d` (which achieves ~4.5:1 on sand)
- Switching section kickers to the ink colour (`#172226`) and reserving gold for decorative non-text uses only
- Using gold only where the background is dark (e.g. the ink-coloured CTA panels, where the contrast is fine)

Reference: [WCAG 2.1 SC 1.4.3](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html)

---

**SHOULD-FIX — MailerLite form on report.html has no persistent visible labels**  
_Affects: report.html, the MailerLite embed form_

The MailerLite form inputs use `aria-label` attributes (`aria-label="name"`, `aria-label="email"`, `aria-label="city"`) and placeholder text, but have no `<label>` elements. Placeholder text disappears when the user starts typing, leaving no visible indication of what the field expects. This fails WCAG 2.1 SC 1.3.5 (Identify Input Purpose) and creates friction for users with cognitive disabilities.

Because this is a MailerLite embed, the fix requires customising the embed HTML to add `<label>` elements above each input — most MailerLite embed editors allow this. Alternatively, add visible labels above the MailerLite form container using plain HTML, outside the embed.

`admin.html` is hidden from the navigation and disallowed in robots.txt, but anyone with the URL can access it and export/modify cms.js content. The admin relies entirely on obscurity. This is low risk given the site's content nature (no sensitive data in the CMS), but worth noting if the site ever manages financially sensitive content.

**SHOULD-FIX — No public Terms of Service page**

The Owner Management Agreement is a legal document for signed clients, not public-facing Terms of Use. Visitors who click Privacy Policy find no corresponding Terms of Service. For a site collecting personal data via Formspree and MailerLite, a basic Terms of Use or Terms of Service page stating the conditions of using the site and submitting applications is standard practice and expected by users. **SHOULD-FIX — CMS admin fields for FAQ 5–8 and hero copy on inner pages are orphaned**  
_(Covered in Technical audit above, but restated here as a gap)_

The gap in practice: a site owner updating the FAQ through the admin panel can successfully edit items 1–4 and see changes. Items 5–8 appear editable but are silently ignored. The same is true for hero copy on why-us.html, areas.html, contact.html, faq.html. This will cause confusion during the first content update cycle.

---

**NICE-TO-HAVE — No About page**

The founder letter on the homepage partially serves this purpose. But visitors who search "About Aurea Hosting" won't find a dedicated page. The founder letter content could be split into a lightweight `/about.html` page, with the homepage showing a truncated excerpt.

---

**NICE-TO-HAVE — cms.js admin lacks any access control or session warning**

The admin page notice says "Changes saved here are in-memory only — they reset on page refresh." A visiting site owner who saves in the admin panel and then closes the browser will lose all their changes unless they remember to download the new `cms.js`. A clear persistent warning ("Your changes are not saved to the server yet") would prevent data loss.

## Recommended Priority Order — Top 5 Fixes

**1. Fix FAQ 5–8 CMS wiring (Critical — silent data loss)**  
Add `data-content="faq5Q"` / `data-content="faq5A"` (through 8) to the span and p elements inside the FAQ accordion items 5–8 in `faq.html`. Straightforward HTML change, 10 minutes.

**2. Fix gold text colour contrast (Critical — WCAG AA failure)**  
Either darken the gold used for text-only contexts (section kickers, eyebrows) to ≥`#9a7a3d`, or change these small-label elements to use the ink colour (`#172226`). Preserving `#c8a35d` for borders, decorative shapes, and button fills is fine — the issue is specifically small-text use on light backgrounds.

**3. Fix double MapLibre initialisation on areas.html (Should-fix — console errors)**  
Remove the inline IIFE map init block from `areas.html` (lines 346–377). `app.js` already initialises the same map with more markers. One-line deletion of a `<script>` block.

**4. Add noindex meta tags to Owner legal doc pages (Should-fix — indexing risk)**  
Two-line addition to `Aurea-Owner-Agreement.html` and `Aurea-Owner-Appointment-Form.html`. Also add `app.js` and `cms.js` script tags to fix the broken mobile nav on those pages.

**5. Wire orphaned admin fields to inner-page HTML, or remove them (Should-fix — content update confusion)**  
The FAQ 5–8 fix (#1) covers part of this. Also add `data-content` attributes to the hero `<h1>` and `<p class="hero-type-sub">` on why-us.html, areas.html, contact.html, faq.html, services.html, and technology.html — matching the keys already defined in cms.js and the admin panel.
